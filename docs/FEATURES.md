# فیچرهای فاز ۱ (Phase-1 Feature Spec)

> **نسخه ۰.۱ — خرداد ۱۴۰۵ — زنده.** مرجعِ استراتژی: [`MASTER_PLAN.md`](MASTER_PLAN.md) · استک: [`TECH_STACK.md`](TECH_STACK.md).
> هدفِ این سند: تبدیلِ «گوهِ مزمن» به مشخصاتِ دقیق و کاربردیِ قابلِ‌ساخت (epic → user story → معیارِ پذیرش).

## دامنه و اصولِ فاز ۱
- **تخصص:** فقط **دیابت + فشار خون** (همان موتورِ موجود) — بدونِ گسترشِ زودهنگام.
- **مشتری:** کلینیکِ **تک‌پزشک تا چندپزشکهٔ کوچک** (نه بیمارستان/HIS).
- **هدفِ تجاری:** «دستیارِ بیماریِ مزمنِ قابلِ‌فروش + نسخهٔ الکترونیک» → ۳ تا ۵ کلینیکِ پولی.
- **بستر:** روی استکِ جدید ([`TECH_STACK.md`](TECH_STACK.md)) با اصلِ **Evolve نه Rewrite** (منطقِ موجود حفظ).

**برچسبِ وضعیت:** ✅ موجود · 🟡 نیمه (هست ولی باید کامل/بازآرایی شود) · 🆕 جدید.
**نقش‌ها:** `پزشک` · `منشی` · `مدیرِ کلینیک` (+ `پرستار` اختیاری).

**اولویتِ ساخت:** `Epic 0` و `Epic 1` (بنیان + بلیتِ ورود) → `Epic 2,3,4` (تجربهٔ متمایز) → `Epic 5,6` (موازی) → `Epic 7` (حفظ/صیقل).

## Epic 0 — بنیانِ SaaS و چندمستأجری 🆕
**چرا:** اپِ فعلی تک‌کلینیکِ desktop است؛ برای فروش باید یک کلینیک بتواند **خودش ثبت‌نام کند، کاربر بسازد و اشتراک بخرد** و دادهٔ هر کلینیک کاملاً ایزوله باشد.

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 0.1 | به‌عنوان مدیرِ کلینیک، می‌خواهم کلینیکم را ثبت‌نام کنم و کاربران بسازم. | فرمِ ثبتِ کلینیک (tenant) + ساختِ کاربر با نقش؛ هر tenant `tenant_id` یکتا. |
| 0.2 | به‌عنوان سیستم، باید دادهٔ هر کلینیک از بقیه ایزوله بماند. | **PostgreSQL RLS** فعال؛ تستِ خودکار: کوئریِ بدونِ `tenant_id` هیچ ردیفی برنمی‌گرداند (deny-by-default). |
| 0.3 | به‌عنوان مدیر، می‌خواهم اشتراک بخرم/تمدید کنم. | پلن‌ها (ماهانه/سالانه)؛ پرداخت از **درگاهِ ایرانی (ZarinPal)**؛ وضعیتِ اشتراک قفل/بازِ دسترسی را کنترل کند. |
| 0.4 | به‌عنوان مدیر، می‌خواهم نقش‌ها و دسترسی‌ها را مدیریت کنم. | RBAC: پزشک/منشی/مدیر؛ بخش‌های بالینی فقط برای کاربرِ دارای **شمارهٔ نظام‌پزشکی** (سپرِ قانونی، [`MASTER_PLAN.md`](MASTER_PLAN.md) §۴.۴). |
| 0.5 | به‌عنوان سیستم، باید فعالیت‌ها را log کنم. | همان `activity_logs` موجود، per-tenant. |

**وابستگی:** اسکیمای Postgres + `tenant_id` همه‌جا (از نقشهٔ مهاجرتِ TECH_STACK §۱۱). **این بنیانِ همهٔ epicهای بعدی است.**

## Epic 1 — نسخهٔ الکترونیک + بیمه ⭐ 🆕 (بلیتِ ورود)
**چرا:** از دی۱۴۰۰ اجباری است؛ بدونِ آن نرم‌افزارِ مطب «قابلِ‌استفاده» نیست. **مهم‌ترین ریسکِ فاز۱.**

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 1.1 | به‌عنوان پزشک، می‌خواهم نسخه را داخلِ نرم‌افزار بنویسم. | کمپوزرِ نسخه: انتخابِ داروی **ژنریک** (از دیتابیسِ دارو)، دوز/تعداد/دستورِ مصرف، اقلامِ خدمت/پاراکلینیک. |
| 1.2 | به‌عنوان پزشک، می‌خواهم نسخه به سامانهٔ بیمهٔ بیمار ثبت شود. | ارسال به **تأمین اجتماعی** و **بیمهٔ سلامت (IHIO)** بر اساس نوعِ بیمهٔ بیمار؛ دریافت/نمایشِ کدِ پیگیری؛ مدیریتِ خطا. |
| 1.3 | به‌عنوان پزشک، نسخهٔ مزمنم باید سریع باشد. | «نسخهٔ تکرارشونده/الگو» برای بیمارِ مزمن (داروهای ثابتِ دیابت/فشار با یک کلیک، از داروهای فعالِ بیمار). |
| 1.4 | به‌عنوان سیستم، باید نسخه را به پروندهٔ بیمار گره بزنم. | نسخه در تایم‌لاینِ بیمار ثبت و در Snapshot دیده شود (Epic 2). |

**✅ Spike انجام شد → [`EPRESCRIPTION.md`](EPRESCRIPTION.md).** اتصالِ مستقیمِ API یک ماراتنِ گواهیِ ۶–۱۲+ ماهه است (گواهیِ افتا + صلاحیتِ هر بیمه). **تصمیمِ de-risk (سه‌مسیره):**
- **MVP:** پُلِ **WebView** (پورتالِ رسمیِ بیمه داخلِ اپ embed) → محصول **بدونِ گواهی فروش‌پذیر** است.
- **موازی، از روزِ اول:** شروعِ فرایندِ گواهیِ افتا/صلاحیت (long-lead)؛ بعداً WebView→API بومی سویچ می‌شود.
- **ارزیابی:** شراکت با فروشندهٔ گواهی‌دار (میان‌بُر).

**اثر:** Epic 1 دیگر **بلاکرِ بقیهٔ فاز۱ نیست**؛ تمرکزِ مهندسی روی لایهٔ تمایز (Epic 2-5) می‌رود.

## Epic 2 — صفحهٔ تصویرِ لحظه‌ایِ بیمار (One-Page Snapshot) 🟡
**وضعیتِ فعلی:** صفحهٔ `patients/detail.html` غنی است و دادهٔ لازم را already دارد (سرویس `get_full_profile` + `control_status` + charts + `snapshot` = آخرین مقدارِ هر شاخص). **ولی** صفحه «کابینِ کامل و قابلِ‌ویرایش» است، نه یک «نمای ۳۰ ثانیه‌ایِ خواندنی».
**هدف:** یک **هدر/نمای خواندنیِ گلانس‌پذیر** که پزشک در ۳۰ ثانیه وضعیت را بفهمد.

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 2.1 | به‌عنوان پزشک، می‌خواهم در یک نگاه مشکلاتِ فعال، داروهای فعلی و آلرژی‌ها را ببینم. | بلوکِ بالای صفحه: `conditions` فعال · `medications` فعال (+ آخرین تغییرِ دوز از `medication_events`) · بنرِ `allergies` (قرمزِ برجسته). |
| 2.2 | به‌عنوان پزشک، می‌خواهم روندِ شاخص‌های کلیدی را با هدف ببینم. | کارت‌های HbA1c/FBS/فشار: مقدارِ آخر + رنگِ سطح (از `evaluate_reading`) + خطِ هدف (`TARGETS`) + اسپارک‌لاینِ روند. |
| 2.3 | به‌عنوان پزشک، می‌خواهم کارهای پیگیرِ باز و آخرین آزمایش‌های مهم را ببینم. | لیستِ `followup_tasks`ِ بازِ سررسیده + آخرین `labs` مهم (HbA1c/LDL/Cr/UACR). |
| 2.4 | به‌عنوان پزشک، می‌خواهم هشدارهای کیفیتِ داده را ببینم. | نوارِ Guardrails (Epic 4) داخلِ Snapshot. |
| 2.5 | جداسازیِ «خواندن» از «ویرایش». | Snapshot فقط خواندنی؛ ویرایش‌ها (ثبتِ شاخص/دارو/فلگ) در تب/مودالِ جدا — صفحه شلوغ نشود. |

## Epic 3 — موتورِ Recall / Care-Plan 🟡
**وضعیتِ فعلی:** `followup_engine.generate_for_patient` پیگیری‌های **ADA-محورِ خودکار** را فقط وقتی **سررسید** شده می‌سازد (a1c هر ۶ ماه، کلیه/لیپید/چشم/پا هر ۱۲، با dedupِ `recently_handled_source`)؛ یک `worklist` هم هست.
**شکاف:** پروتکلِ **قابلِ‌تعریفِ پزشک** نیست؛ و **KPIِ مدیر** (درصدِ پیگیریِ انجام‌شده) نیست.

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 3.1 | به‌عنوان پزشک، می‌خواهم پروتکلِ پیگیریِ دلخواه بسازم. | سازندهٔ قاعده: «اگر [رویداد: شروعِ داروی X / ثبتِ HbA1c / تشخیصِ Y] → بعد از N روز، [پیگیری/یادآور/چک‌لیست]». ذخیره per-tenant. |
| 3.2 | به‌عنوان منشی، می‌خواهم «لیستِ کارهای امروز» را ببینم. | worklistِ موجود + فیلترِ امروز/عقب‌افتاده + اکشنِ «انجام شد/تماس گرفته شد/زمان‌بندیِ مجدد». |
| 3.3 | به‌عنوان پزشک، پیگیری باید فقط وقتی سررسیده ساخته شود (نه اسپم). | منطقِ «due-only»ِ موجود حفظ شود؛ پروتکل‌های دستی هم همین رفتار. |
| 3.4 | به‌عنوان مدیر، می‌خواهم نرخِ تکمیلِ پیگیری را ببینم. | KPI: «٪ پیگیری‌های انجام‌شدهٔ این ماه» (به Epic 5 وصل). |
| 3.5 | پیگیری بتواند پیامکِ خودکار بفرستد. | اتصالِ تسکِ پیگیری به کمپین/یادآورِ پیامکی (Epic 6). |

## Epic 4 — نگه‌بانِ کیفیتِ داده (Data-Quality Guardrails) 🆕
**چرا:** کمکِ کیفیت **بدونِ توصیهٔ درمانی** → ریسکِ قانونیِ پایین + ارزشِ واقعی برای پزشک. تمایزی که رقبا ندارند.
**اصل:** سیستم «درمان پیشنهاد نمی‌کند»؛ فقط می‌گوید چه چیزی **ناقص** است.

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 4.1 | به‌عنوان پزشک، می‌خواهم نقص‌های پرونده به من گوشزد شود. | تشخیصِ خودکار: «آلرژی ثبت نشده» · «داروی بدونِ دوز» · «تشخیص بدونِ برنامهٔ پیگیری» · «شاخصِ کلیدیِ قدیمی (مثلاً HbA1c > ۶ ماه)». |
| 4.2 | هشدارها باید عملی باشند. | هر هشدار یک لینکِ مستقیم به فرمِ اصلاح دارد. |
| 4.3 | نباید مزاحم باشد. | قابلِ رد/خاموش‌کردنِ موردی؛ در Snapshot جمع‌وجور. |

## Epic 5 — هوشِ کلینیک (Practice Intelligence) 🟡
**وضعیتِ فعلی:** `analytics_service` تحلیلِ **per-patient** دارد. **شکاف:** گزارشِ **سطحِ کلینیک/کوهورت** نیست.
**چرا:** این همان چیزی است که فروشِ اشتراک را قانع می‌کند («نرم‌افزارت نشان می‌دهد درمانت بهتر شده»).

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 5.1 | به‌عنوان پزشک، می‌خواهم بدانم کنترلِ بیمارانم چطور است. | داشبوردِ کوهورت: «٪ دیابتی‌های با HbA1c < ۷»، «٪ فشارِ کنترل‌شده»، روندِ ۶ ماهه. |
| 5.2 | به‌عنوان پزشک، می‌خواهم بیمارانِ پرخطر/عقب‌افتاده را پیدا کنم. | لیستِ «نیازمندِ توجه»: پیگیریِ عقب‌افتاده، شاخصِ خارج از هدف، عدمِ مراجعه. |
| 5.3 | به‌عنوان مدیر، می‌خواهم KPIهای عملیاتی ببینم. | تعدادِ بیمارِ فعال، نرخِ تکمیلِ پیگیری، درآمد (از ماژولِ حسابداریِ ادغام‌شده). |

## Epic 6 — یادآور و کمپینِ پیامکی ✅ (صیقل)
**وضعیتِ فعلی:** کامل — `campaign_service` + مدیانا + کیف‌پول + `compliance` (بازنویسیِ کلماتِ ممنوعه).

| # | User Story | معیارِ پذیرش |
|---|---|---|
| 6.1 | یادآورِ خودکارِ نوبت/پیگیری. | اتصالِ `followup_tasks` و `appointments` به ارسالِ پیامکِ زمان‌بندی‌شده. |
| 6.2 | کمپینِ گروهی (موجود) per-tenant شود. | کلیدهای مدیانا و کیف‌پول در سطحِ tenant. |

## Epic 7 — پشتیبانِ بالینیِ ADA ✅ (حفظ — پلِ فاز ۲)
**وضعیتِ فعلی:** کامل — `rule_engine.grouped` (~۵۷ قاعده)، پنلِ `analytics.html`، `suggestion_log` (اعمال/رد)، ماشین‌حسابِ انسولین.
**کارِ فاز۱:** فقط **حفظ + صیقل + تقویتِ سپرِ قانونی**: دیسکلیمرِ «پیشنهاد، تأیید با پزشک» پررنگ‌تر و **log‌شدنِ دیدن/رد**، و محدودسازی به کاربرِ پزشک. (این موتور، بذرِ «دستیارِ درمان»ِ فاز۳ است — دست‌نخورده و قوی نگه داشته شود.)

## وابستگی‌ها و ترتیبِ پیشنهادی
```
Epic 0 (بنیان SaaS) ──┬─→ Epic 1 (نسخه، بلیت ورود)   ← Spike اول
                      ├─→ Epic 2 (Snapshot)
                      ├─→ Epic 3 (Recall) ─→ Epic 6 (پیامک)
                      ├─→ Epic 4 (Guardrails)
                      └─→ Epic 5 (Practice Intelligence)
Epic 7 (ADA) — موجود، فقط حفظ/صیقل
```

## معیارهای موفقیتِ فاز ۱
- **۳ تا ۵ کلینیکِ پولیِ فعال.**
- **نرخِ تکمیلِ پیگیری (recall completion)** بالای آستانهٔ توافقی.
- **Retention** کلینیک‌ها پس از ۳ ماه.
