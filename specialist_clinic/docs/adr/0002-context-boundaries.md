# ADR-0002 — مرزِ Bounded Contextها و مالکیت

- **وضعیت:** پذیرفته‌شده — ۱۴۰۵/۰۳/۳۰ (۲۰۲۶-۰۶-۲۰)
- **مرتبط:** [ADR-0001](0001-evolve-not-rewrite.md) · [ADR-0003](0003-integration-seam-outbox.md) · [Context Map](../architecture/context-map.md)

## زمینه
جریانِ کاریِ پزشک کلِ کلینیک را دربر می‌گیرد (پذیرش → صفِ پزشک → ویزیت → اقدام/پیام)، و این جریان از مرزِ دو اپ + یک ترکِ موازی (پل نسخه‌نویسی) عبور می‌کند. برای جلوگیری از درهم‌رفتنِ منطقِ پولی و بالینی، مرزها باید صریح باشند.

## تصمیم
سه **Bounded Context**:

1. **حسابداری / پذیرش (`webapp`) — Upstream.** مالکِ: **هویتِ بیمار (`national_id`)**، فاکتور، ویزیت، تزریق، پروسیجر، پول. **منتشرکنندهٔ رویداد.** از وجودِ اپِ تخصصی بی‌خبر می‌ماند.
2. **بالینی / تعامل (`specialist_clinic`) — Downstream.** مالکِ: `patient_links` (آینهٔ محلی)، پروندهٔ بالینی، موتورِ قاعده/تعامل، SMS، صفِ تأیید، ورک‌لیست. رویدادهای حسابداری را از طریقِ **Anti-Corruption Layer (ACL)** — یعنی پلِ read-only + مصرف‌کنندهٔ رویداد — مصرف می‌کند.
3. **پل نسخه‌نویسی — Context سومِ مستقل** (کدبیسِ جدا، اکستنشنِ MV3). ACLِ خودش به پنل‌های بیمه. **در هیچ‌کدام از دو Context هضم نمی‌شود.**

**رابطه:** Customer-Supplier (حسابداری=تأمین‌کننده/upstream، تخصصی=مشتری/downstream) با ACL در سمتِ تخصصی. **جهتِ وابستگی یک‌طرفه: تخصصی به حسابداری وابسته است، نه برعکس** — این مرز را تمیز نگه می‌دارد و T4 (نوشتنِ معکوس) را عقب می‌اندازد.

**هویت:** مالکش حسابداری است؛ تخصصی با `national_id` آینه می‌کند (`patient_links`). **Shared Kernel نمی‌شود.**

### جای‌گذاریِ قابلیت‌های مرزی (با دلیل)

| قابلیت | Context | چرا |
|---|---|---|
| صفِ تأییدِ پزشک | تخصصی (هست) | تصمیمِ بالینی/تعاملی؛ `engagement_approvals` (`engagement_repo.py:114`) |
| پیامکِ تشکر (پس از بستنِ فاکتور) | تخصصی، با **تریگرِ رویدادِ `invoice.closed`** | محتوا/کانال/گاردریل دانشِ تعامل است؛ «فاکتور بسته شد» را حسابداری منتشر می‌کند |
| دعوتِ پروسیجر (گوش/پانسمان/بخیه) | تخصصی | از آیتم‌های فاکتورِ بسته‌شده مشتق می‌شود (همان رویدادِ `invoice.closed`) |
| صفِ زندهٔ پزشک (بیمارانِ امروز) | تخصصی، **خواندنِ زندهٔ فاکتورهای باز از پل** (نه رویداد) | ساده‌تر؛ نیازی به Outbox ندارد |
| کارتِ عمومیِ بیمار | تخصصی (نمای توکن‌دار)، **هویت از حسابداری** | دموگرافیک مالِ حسابداری؛ تخصصی فقط دادهٔ بالینیِ خودش را نشان می‌دهد |

## پیامدها
- ✅ مرزِ پول/بالین تمیز؛ هیچ منطقِ بالینی به حسابداری نشت نمی‌کند و هیچ نوشتنِ پولی به تخصصی نمی‌آید.
- ⚠️ تخصصی برای دموگرافیک به پل وابسته است (`accounting_bridge.get_patient_by_national_id:89`). تا read-only/live است سالم؛ اگر روزی تخصصی بخواهد بیمار بسازد (PWA)، رویدادِ `patient.registered` به Event Catalog افزوده شود (نسخهٔ بعد، نه v1).
