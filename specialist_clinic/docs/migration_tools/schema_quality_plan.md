# پلنِ ارتقای کیفیتِ مدلِ داده (پساٰ-آدیتِ ۵-زاویه‌ای)

> **زمینه (۲۰۲۶-۰۶-۲۴):** مالک مهاجرتِ دادهٔ قدیمی را **کنار گذاشت**؛ اولویتِ مطلق = **کیفیتِ پلتفرم و مدلِ جدید**. این آزاد می‌کند تغییراتی را که قبلاً «سخت‌برای‌مهاجرت» بودند (تنگ‌کردنِ نوع، NOT NULL، حذفِ کوئرک‌های legacy، تبدیلِ BOOLEAN). منبع: سنتزِ آدیتِ تهاجمیِ ۵ مشاور (data · architecture · security · clinical-product · backend/ORM) روی برش‌های ۰/۲/۳/۴.
>
> هر بَچ روی کانتینرِ Docker (PG16) اعتبارسنجی می‌شود و هارنسِ `tests/test_pg_schema.py` سبز می‌ماند/گسترش می‌یابد. هیچ‌چیز شکسته نمی‌شود چون اپِ لوکالِ فعلی روی SQLite کار می‌کند و این فایل‌ها فقط schemaِ پلتفرمِ جدیدند.

## تصمیم‌های قفل‌شده (رفعِ تعارض‌های آدیت)
- **بولی → `BOOLEAN` همه‌جا.** دلیلِ تاریخیِ `SMALLINT` («کدِ پایتونِ `=1` مقایسه می‌کند») مخصوصِ Flask/SQLite بود؛ با Django + حذفِ مهاجرت باطل است. برشِ ۰ هم از قبل BOOLEAN است → یکدست‌سازی.
- **id-strategy → `GENERATED BY DEFAULT AS IDENTITY` همه‌جا.** Django در `bulk_create`/fixture/تست id صریح می‌دهد؛ `ALWAYS` خطا می‌دهد. (trade-off: ریسکِ sequence-drift اگر کد دستی id بدهد — با انضباطِ ORM پوشش داده می‌شود.)
- **FKهای tenant → مرکب.** هر والدِ per-tenant `UNIQUE(tenant_id, id)` می‌گیرد و FKهای intra-schema به `(tenant_id, parent_id)` ارتقا می‌یابند (الگوی درستِ برشِ ۴ به داخل تعمیم می‌یابد). این تنها چیزی است که در T1 «واقعاً گران» می‌شد.
- **`invoice_item_payments` → افزودنِ `id` surrogate + نگه‌داشتنِ کلیدِ مرکب به‌صورتِ UNIQUE** (Django PK مرکب را خوب پشتیبانی نمی‌کند).
- **ICD/کدگذاریِ تشخیص → موکولِ تصمیمِ مالک** (گسترشِ scopeِ محصول؛ نیازِ روشن‌شدنِ workflowِ پزشک). بقیهٔ نقص‌های دامنه (encounters/doctor_id/دوز/آلرژی/prescription_items) اجرا می‌شوند.
- **`full_name` STORED حفظ می‌شود** (طراحیِ خوب)؛ صرفاً در لایهٔ اپ با `GeneratedField` (Django 5+) مدل می‌شود — یادداشتِ اپ، نه تغییرِ schema.

---

## بَچ ۱ — یکدستیِ نوع و کنوانسیون (ORM-ready)
*ریسکِ پایین، هم‌گراییِ بالا، بنیادی (همه‌چیز رویش ساخته می‌شود).*
1. همهٔ ستون‌های بولیِ `SMALLINT` در برش‌های ۲/۳ → `BOOLEAN NOT NULL DEFAULT TRUE/FALSE`. (is_active، is_paid، covered_by_insurance، patient_provided، is_exception، nursing_covers «باگ حفظ‌شده»→BOOLEAN با همان DEFAULT FALSE، is_supplementary، is_base/is_base_tariff، glucose_lowering، is_custom، outreach_done، …)
2. همهٔ `GENERATED ALWAYS AS IDENTITY` (برشِ ۰: users، patient_links؛ برشِ ۲: جداولِ تراکنشی) → `BY DEFAULT`.
3. `accounting.invoice_item_payments`: افزودنِ `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`؛ کلیدِ `(tenant_id, invoice_id, item_type, item_id)` → `UNIQUE`.

## بَچ ۲ — یکپارچگیِ ارجاعی و constraintها
*برد کیفیتیِ زیاد؛ نگرانیِ دادهٔ یتیم با حذفِ مهاجرت رفع شد.*
4. **CHECK روی status/enumها:** `invoices.status (open|closed)` [بحرانیِ مالی]، `visits.status/payment_status`، `appointments.status`، `followup_tasks.status/fulfillment`، `suggestion_log.status`، `engagement_approvals.status`، `sms_messages.status`، `sms_campaigns.status/campaign_type`، `engagement_events.channel/category`، `users.role/app`، `procedures.performer_type`، `consumables*.category (drug|supply)`، `medical_staff.staff_type` (موجود). (`shift` عمداً بدونِ CHECK.)
5. **FK واقعی روی «FK منطقی»‌ها (intra-schema):** `medication_events.medication_id`، `appointments.parent_appointment_id` (self، SET NULL)، `followup_tasks.appointment_id`، `prescriptions.followup_task_id`/`prescriber_user_id→platform.users`، `engagement_approvals.appointment_id`، `wallet_transactions.campaign_id`، و FKهای مرکبِ کاتالوگ `(tenant_id,key)`: `lab_results.test_key`، `patient_medications.drug_class`، `patient_flags.flag_key`، `engagement_dispatch.event_key`.
6. **FKهای مرکبِ tenant + `UNIQUE(tenant_id,id)`** روی والدها (تصمیمِ قفل‌شده).
7. **`ON DELETE` صریح:** RESTRICT روی والدهای بالینی، SET NULL روی لینک‌های اختیاری (وعدهٔ ADR §۵ که پیاده نشده).
8. **CHECKهای دامنه/بازه:** `*_percent BETWEEN 0 AND 100`، `vital_readings.value > 0`، `sms_campaigns.*_count >= 0`.

## بَچ ۳ — کیفیتِ امنیت/حریم در سطحِ مدل
9. **`platform.users.api_token` → هش:** `api_token_hash BYTEA` + `api_token_prefix TEXT` (مثلِ Git PAT)؛ index روی hash. (هماهنگیِ کدِ Flaskِ پلِ نسخه‌نویسی در لایهٔ اپ.)
10. **`settings` (هر دو) → آماده‌رمز:** `is_sensitive BOOLEAN` + `value_encrypted BYTEA`؛ کلیدِ SMS/توکن در `value` خام نماند.
11. **محدودسازیِ GRANTِ `clinical_app`** روی accounting: فقط `patients، invoices، visits، injections، procedures، consumables_ledger` — **نه** `payroll_settings/settings/medical_staff`. حذفِ `ALTER DEFAULT PRIVILEGES`ِ کلی برای accounting→clinical.
12. **`clinical.activity_logs`** (غایب) ساخته شود — auditِ دسترسی/تغییرِ PHI بالینی (متقارنِ accounting).
13. **حذفِ `national_id` از لجرهای مرزی** (`processed_invoices`/`doctor_visit_log`) → به‌جایش `patient_uuid`؛ + `sms_consent_at/source/opt_out_at/data_retention_until` روی `patient_links`؛ + `sms_messages.recipient` → ارجاع به patient، نه شمارهٔ خام.

## بَچ ۴ — کیفیتِ دامنهٔ بالینی/مالی + پولیش
14. **`clinical.encounters`** (موجودیتِ غایبِ حیاتی): `(patient_link_id, doctor_id, encounter_type, encounter_at, chief_complaint, status)`؛ FK از `vital_readings`/`lab_results`/`prescriptions`/`clinical_notes` به آن (nullable در گذار). رابطه با `doctor_visit_log` (state-machine) تعریف شود.
15. **`appointments`** + `doctor_id → medical_staff` + `reason TEXT`.
16. **دوزِ ساختاریافته:** `patient_medications` + `dose_value NUMERIC، dose_unit TEXT، frequency TEXT CHECK، route TEXT` (کنارِ `dose/schedule` متنی).
17. **`allergies.severity` CHECK** (`mild|moderate|severe|anaphylaxis`) + لینکِ `drug_class_key` برای drug-safety rules.
18. **`clinical.prescription_items`** (به‌جای فقط `prescriptions.items JSONB`): query/analyticsِ «کدام دارو بیشتر تجویز شده».
19. **`observations` VIEW:** namespaceِ `obs_key` (`'vital:'||type` / `'lab:'||…`) + JOINِ `ref_low/ref_high` از `clinical_indicators`.
20. **`updated_at`** روی جداولِ ویرایش‌پذیر (appointments، followup_tasks، patient_conditions، sms_campaigns، …) + triggerِ خودکار.
21. **مستندسازیِ DAGِ سه‌سطحی** در ADR-0007: `clinical → accounting → platform` + `clinical → platform` (مرزِ واقعی دوتایی نیست).

## موکول به تصمیمِ مالک
- **کدگذاریِ ICD/تشخیصِ ساختاریافته** (clinical P0-B): گسترشِ scopeِ محصول. آیا پلتفرم باید تشخیصِ کدشده (ICD-10) per-encounter داشته باشد؟ → اگر بله، جدولِ `diagnoses` + `icd_code/version`.
- **تبدیلِ کاملِ BOOLEAN**: تصمیم گرفته شد (بَچ ۱)؛ صرفاً یادآوری که کوئری‌های اپِ آینده باید BOOLEAN-aware نوشته شوند (مشکلِ کدِ قدیمی نیست چون اپِ جدید از صفر است).
