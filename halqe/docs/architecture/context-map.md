# Context Map — نقشهٔ Bounded Contextها

مرجع: [ADR-0002](../adr/0002-context-boundaries.md). این نقشه «as-is»ِ تکامل‌یافته است (دو اپِ Flask + ترکِ موازی)، که درزش همان است که پلتفرمِ آیندهٔ کارفرما پیاده خواهد کرد.

```
        ┌─────────────────────────────┐        رویدادها (Outbox)        ┌──────────────────────────────────┐
        │  حسابداری / پذیرش (webapp)   │  ───── invoice.closed ─────▶   │  بالینی / تعامل (specialist)      │
        │  Bounded Context — UPSTREAM  │                                │  Bounded Context — DOWNSTREAM     │
        │                             │  ◀── خواندنِ زندهٔ فاکتورِ باز ──  │  ACL = accounting_bridge (mode=ro)│
        │  مالک: هویت(national_id)،    │       + درآمد/دموگرافیک         │       + مصرف‌کنندهٔ رویداد          │
        │  فاکتور، ویزیت، تزریق،       │       (read-only)               │  مالک: patient_links(آینه)،        │
        │  پروسیجر، پول                │                                │  پروندهٔ بالینی، موتورِ تعامل/پیگیری،│
        │  (منتشرکنندهٔ رویداد)         │                                │  SMS، صفِ تأیید، ورک‌لیست           │
        └─────────────────────────────┘                                └──────────────────────────────────┘
                  │ بی‌خبر از وجودِ تخصصی                                          │
                  │ (فقط رویداد منتشر می‌کند)                                      │ تنها سطحِ بیرونی:
                  ▼                                                               ▼ نمای عمومیِ توکن‌دارِ بیمار (آینده)
        رابطه: Customer-Supplier + ACL   ·   جهتِ وابستگی یک‌طرفه: تخصصی → حسابداری (هرگز برعکس)

        ┌─────────────────────────────────────────────┐
        │  پل نسخه‌نویسی (Context سومِ مستقل)            │   ACLِ خودش   ▶  پنل‌های بیمهٔ وب (تأمین/سلامت/…)
        │  کدبیسِ جدا، اکستنشنِ مرورگرِ MV3              │   روی لاگینِ خودِ پزشک
        │  در هیچ‌کدام از دو Context هضم نمی‌شود         │
        └─────────────────────────────────────────────┘
```

## روابط و قواعد
- **Upstream/Downstream:** حسابداری بالادست (منبعِ حقیقتِ پول + هویت + رویداد)؛ تخصصی پایین‌دست. **هیچ منطقِ بالینی در حسابداری، هیچ نوشتنِ پولی در تخصصی.**
- **ACL:** تخصصی هرگز مدلِ خامِ حسابداری را به دامنهٔ خودش راه نمی‌دهد؛ همه‌چیز از `accounting_bridge` (فقط‌خواندنی) و مصرف‌کنندهٔ رویداد عبور می‌کند.
- **یک‌طرفه‌بودنِ وابستگی** عمدی است: T4 (نوشتنِ معکوس) را تا حدِ امکان عقب می‌اندازد و قانونِ read-only را حفظ می‌کند.
- **پل نسخه‌نویسی** جدا می‌ماند چون چرخهٔ عمر/ریسک/کدبیسِ متفاوتی دارد (DOMِ شکنندهٔ پنل‌های بیمه).

## نگاشت به دیاگرامِ کارفرما (to-be)
«قلبِ» دیاگرام (CareProtocol → Enrollment → followup_tasks → dispatch → Messaging) **همین حالا داخلِ Context تخصصی ساخته شده**. درزِ Outbox (ADR-0003) = نسخهٔ مینیمالِ «Event Bus»ِ دیاگرام. مهاجرتِ آینده (Strangler، تریگرهای ADR-0001) این دو Context را به مونولیتِ ماژولارِ Django/Postgres با همان مرزها منتقل می‌کند؛ پلِ نسخه‌نویسی مستقل می‌ماند.
