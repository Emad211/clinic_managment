# انتقال کامل حسابداری به حلقه

## هدف

هدف نهایی حذف وابستگی عملیاتی به `webapp` و اجرای پذیرش، فاکتور، خدمات، پرداخت،
تعرفه، شیفت، گزارش و حقوق در `halqe` است؛ بدون بازنویسی ناگهانی منطق مالی و بدون
تغییر خاموش در خروجی تاریخی.

`webapp` تا پایان cutover، **oracle رفتار تولیدی** باقی می‌ماند. جدول‌های PostgreSQL
در `accounting.*` از قبل وجود دارند؛ مهاجرت باقی‌مانده عمدتاً انتقال commandها،
projectionها، UI، تست‌های تطبیقی و داده است.

## اصول غیرقابل مذاکره

1. هیچ تغییر پولی بدون golden-master/characterization test پذیرفته نمی‌شود.
2. عملیات حسابداری فقط با LOGIN نقش `accounting_app` انجام می‌شود؛ نقش عادی حلقه
   همچنان روی `accounting.*` فقط خواندنی است.
3. هر command مالی tenant-scoped، اتمیک و audit‌شده است.
4. پول در PostgreSQL عدد صحیح تومان (`NUMERIC(14,0)`) است.
5. فاکتور مهاجرت‌یافته با موتور قیمت‌گذاری ناشناخته، توسط موتور جدید دوباره محاسبه
   یا بسته نمی‌شود. `pricing_version` این مرز را صریح می‌کند.
6. rollout مرحله‌ای، dual-run، reconciliation و rollback اجباری‌اند.

## وضعیت فازها

### A — هستهٔ پذیرش و فاکتور ویزیت

دامنه:

- نقش نوشتن مستقل حسابداری؛
- جست‌وجو/ثبت/به‌روزرسانی بیمار؛
- خواندن تعرفه‌های ویزیت؛
- بازکردن اتمیک فاکتور + ویزیت؛
- فهرست فاکتورهای باز؛
- بستن فاکتورهای `halqe_visit_v1`؛
- audit trail؛
- صفحهٔ RTL حسابداری در Next.js.

گیت ایمنی: فاکتورهای legacy یا دارای تزریق، پروسیجر و مصرفی در این فاز از مسیر جدید
بسته نمی‌شوند.

### B — تزریق، خدمات پرستاری، پروسیجر و مصرفی

برای هر خانواده به‌ترتیب:

1. استخراج characterization testهای متناظر از `webapp`؛
2. تعریف snapshot قیمت و سهم بیمار/بیمه؛
3. port سرویس + repository + API + UI؛
4. oracle comparison روی fixture و کپی sanitize‌شدهٔ دادهٔ واقعی؛
5. حذف guard همان خانواده پس از تطبیق صددرصدی.

ترتیب پیشنهادی: تزریق/پرستاری → پروسیجر → مصرفی.

### C — پرداخت و بستن کامل فاکتور

- وضعیت پرداخت آیتمی؛
- نقد/کارت/بیمه؛
- مانده، مبلغ وصول‌شده و رسید؛
- state machine فاکتور؛
- جلوگیری از double-close/double-payment؛
- reconciliation سه‌گانه:
  - `billed/raw service revenue`
  - `patient liability`
  - `collected`

### D — تنظیمات عملیاتی

- پزشک/پرستار و اتصال user↔staff؛
- شیفت فعال و تاریخ کاری؛
- تعرفه‌های پایه/تکمیلی؛
- استثناهای پوشش پرستاری؛
- کاتالوگ خدمات و قیمت‌ها؛
- import/export تنظیمات per-tenant.

### E — مدیریت، گزارش و حقوق

- داشبورد مالی؛
- گزارش بیمار، فاکتور، ویزیت، تزریق، پروسیجر و مصرفی؛
- payroll و درصدها؛
- خروجی CSV/Excel؛
- audit search و retention؛
- تطبیق تمام queryهای گزارش با oracle تولیدی.

### F — ETL، dual-run و cutover

1. backup رمزگذاری‌شده + `PRAGMA integrity_check` روی SQLite؛
2. ETL preserve-id و `setval` برای همه identityها؛
3. تبدیل کنترل‌شدهٔ تاریخ/boolean/money؛
4. ثبت manifest و checksum هر جدول؛
5. اجرای سه oracle مالی قبل/بعد؛
6. dual-run محدود با write فقط در یک منبع و مقایسهٔ خروجی؛
7. freeze پنجرهٔ cutover، delta import و smoke test؛
8. فعال‌کردن حسابداری حلقه برای پذیرش؛
9. نگهداری `webapp` به‌صورت read-only در دورهٔ rollback؛
10. حذف نهایی فقط پس از sign-off مالک و حسابدار.

## تعریف Done برای انتقال کامل

- تمام جریان‌های عملیاتی `webapp` در حلقه موجود باشند؛
- هیچ route یا گزارش روزمره‌ای به SQLite وابسته نباشد؛
- oracleهای مالی روی دادهٔ مهاجرت‌یافته بدون اختلاف باشند؛
- تست permission ثابت کند نقش clinical قادر به write حسابداری نیست و نقش accounting
  قادر به خواندن `clinical.*` یا `platform.users` نیست؛
- backup/restore و rollback تمرین شده باشد؛
- حداقل یک دورهٔ مالی واقعی در dual-run بدون اختلاف بسته شده باشد؛
- سپس `webapp` از production خارج و فقط archive شود.
